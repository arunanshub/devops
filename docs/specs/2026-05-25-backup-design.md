# Backup and Restore Design

**Date:** 2026-05-25
**Status:** Approved for implementation

## Problem

The cluster has no backup infrastructure. ArgoCD + git covers the vast majority of disaster recovery (cluster objects, workload config, secrets via SealedSecrets), but two gaps remain:

1. **Dynamic cluster state not captured in git** — PVC/PV binding metadata, in-cluster CRs generated by operators, anything not committed.
2. **etcd corruption or cluster loss** — GitOps rebuild takes ~45 minutes and is clean, but etcd snapshots are faster for partial state recovery and required for scenarios where git state alone is insufficient.

A secondary goal is operational confidence: backup health must be observable through the existing Prometheus/Alertmanager/Grafana pipeline, and the restore path must be exercised regularly so failures are discovered in drills rather than disasters.

## Scope

**Covered:**
- etcd snapshots → Cloudflare R2 (k3s built-in S3 upload, every 6h)
- Full-cluster Kubernetes object backups → Cloudflare R2 (Velero, daily, no FSB)
- Observability: Velero Prometheus metrics + kube-state-metrics CronJob health → PrometheusRules → existing Alertmanager email pipeline
- Monthly automated restore drill (Velero, into ephemeral test namespace)
- Manual restore runbooks as `just` recipes

**Explicitly not covered:**
- Persistent volume data backup (FSB off — Prometheus/Tempo/Grafana accept data loss on cluster rebuild)
- Tempo S3 backend migration (deferred until object storage budget allows)
- Automated etcd restore drill (cluster-reset is live-cluster-destructive; manual runbook only)

## Storage

Two Cloudflare R2 buckets provisioned in `infra/cloudflare.tf`:

| Bucket | Contents | Retention |
|---|---|---|
| `arunanshu-etcd-snapshots` | Compressed etcd snapshots | 24 local / 48 S3 (≈12 days at 6h cadence) |
| `arunanshu-velero-backups` | Velero backup tarballs + metadata | 30 daily backups |

Object versioning enabled on both buckets. A lifecycle rule (`noncurrent_version_expiration: 30 days`) prevents versioned objects from accumulating past the R2 free tier — without it, every Velero TTL-expiry and k3s snapshot rotation leaves a versioned object that persists indefinitely.

Two scoped R2 API tokens (one per bucket, S3 read/write) provisioned alongside the buckets. Credentials flow: OpenTofu outputs → `just seal-etcd-s3` / `just seal-velero-s3` → SealedSecrets.

## Components

Eight components across four areas of the repo.

### 1. OpenTofu — `infra/cloudflare.tf`

- `cloudflare_r2_bucket` for each bucket
- `cloudflare_r2_bucket_lifecycle_configuration` for noncurrent version expiration
- `cloudflare_api_token` resources scoped per bucket (R2 read/write)
- Outputs: S3 endpoint, access key ID, secret access key per bucket

**Prerequisite:** The existing `var.cloudflare_api_token` almost certainly lacks R2 management and API-token-creation permissions. Before running `tofu apply`, update the token in the Cloudflare dashboard to include R2 permissions. This cannot be automated from the existing token.

### 2. Ansible — `ansible/playbooks/k3s-etcd-snapshots.yml`

Same pattern as `k3s-eviction.yml`: targets CP nodes only, drops a config drop-in at `/etc/rancher/k3s/config.yaml.d/etcd-snapshots.yaml`, restarts k3s serially (one node at a time), waits for node Ready before proceeding. One-shot; not imported into `site.yml`.

The drop-in content:
```yaml
etcd-s3: true
etcd-s3-config-secret: k3s-etcd-snapshot-s3-config
etcd-snapshot-schedule-cron: "0 */6 * * *"
etcd-snapshot-retention: 24
etcd-s3-retention: 48
etcd-snapshot-compress: true
```

**Bootstrap ordering constraint:** This playbook must run *after* ArgoCD has reconciled the sealed-secrets controller AND the `k3s-etcd-snapshot-s3-config` SealedSecret has been applied in `kube-system`. Running it before the Secret exists is safe (k3s starts and retries), but the first snapshot uploads will fail until the Secret appears. Do not run during bootstrap before step 5 (`just argocd-root-bootstrap`).

**k3s + R2 compatibility:** k3s uses the minio Go S3 client. A `ListObjectsV2` metadata incompatibility with R2 was fixed in k3s 1.27; this cluster runs 1.35.4. The Secret must include `etcd-s3-bucket-lookup-type: path` (R2 requires path-style URLs). No checksum header issue (unlike Velero's AWS plugin — different code path).

The `k3s-etcd-snapshot-s3-config` Secret shape:
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: k3s-etcd-snapshot-s3-config
  namespace: kube-system
type: etcd.k3s.cattle.io/s3-config-secret
stringData:
  etcd-s3-endpoint: "https://<account_id>.r2.cloudflarestorage.com"
  etcd-s3-access-key: "<ACCESS_KEY>"
  etcd-s3-secret-key: "<SECRET_KEY>"
  etcd-s3-bucket: "arunanshu-etcd-snapshots"
  etcd-s3-region: "auto"
  etcd-s3-bucket-lookup-type: "path"
  etcd-s3-folder: "prod"
  etcd-s3-insecure: "false"
  etcd-s3-timeout: "5m"
```

Strip `creationTimestamp`, `resourceVersion`, `uid`, `ownerReferences` before sealing (per CLAUDE.md).

### 3. Velero — `kubernetes/base/platform/velero/`

ArgoCD Application + `values.yaml`. Follows the platform AppProject conventions from `docs/specs/2026-05-24-kustomize-appproject-reorganization.md`:
- `project: platform`
- Add `velero` namespace to platform AppProject destinations
- Add `https://vmware-tanzu.github.io/helm-charts` to platform AppProject `sourceRepos`

Chart: `vmware-tanzu/velero` v12.x (chart major = Velero minor; 12.x = Velero 1.18.x).

Key values:
```yaml
nodeAgent:
  enabled: false  # FSB off — no PV data backup

configuration:
  backupStorageLocation:
    - name: default
      provider: aws
      bucket: arunanshu-velero-backups
      credential:
        name: velero-r2-credentials
        key: cloud
      config:
        region: auto
        s3Url: "https://<account_id>.r2.cloudflarestorage.com"
        s3ForcePathStyle: "true"
        checksumAlgorithm: ""  # R2 rejects AWS checksum headers

schedules:
  daily-full:
    schedule: "0 2 * * *"
    template:
      ttl: 720h  # 30 days
      includedNamespaces:
        - "*"
      includeClusterResources: true

metrics:
  enabled: true
  serviceMonitor:
    enabled: true
    # Prometheus picks this up via serviceMonitorSelectorNilUsesHelmValues: false
```

The Velero credentials Secret uses AWS credentials file format:
```
[default]
aws_access_key_id = <access_key>
aws_secret_access_key = <secret_key>
```
Sealed as `velero-r2-credentials` in the `velero` namespace.

**S3 restore constraint:** The S3 config Secret cannot be used during etcd restore (apiserver is unavailable). S3 credentials must be passed via CLI flags directly when restoring an etcd snapshot from R2. Document in `just etcd-restore`.

### 4. etcd Snapshot Health CronJob — `kubernetes/components/etcd-snapshot-health/`

Component kustomization (`kind: Component`), `project: infra`, deploys to `kube-system`.

Runs every 8 hours. Uses `amazon/aws-cli` image. Mounts the `k3s-etcd-snapshot-s3-config` Secret (already in `kube-system`). Lists the etcd snapshot bucket, finds the most-recent object's last-modified timestamp, exits 0 if a snapshot was uploaded within the last 10 hours, exits 1 otherwise.

kube-state-metrics (already in kube-prometheus-stack) exposes `kube_cronjob_status_last_successful_time` — no Pushgateway needed. Alert fires if `time() - kube_cronjob_status_last_successful_time > 36000` (10h; 6h cadence + 4h buffer).

### 5. Velero Restore Drill CronJob — `kubernetes/components/velero-restore-drill/`

Component kustomization (`kind: Component`), `project: platform`, deploys to `velero` namespace.

Runs monthly (1st of month, 08:00 UTC). Uses `velero/velero` image.

Drill sequence:
1. Delete `velero-restore-test` namespace if it exists (idempotent cleanup)
2. Find the latest `Completed` backup from the daily schedule
3. Create a scoped restore:
   ```bash
   velero restore create "$RESTORE_NAME" \
     --from-backup "$LATEST_BACKUP" \
     --include-namespaces monitoring \
     --include-cluster-resources=false \
     --namespace-mappings "monitoring:velero-restore-test"
   ```
4. Wait for restore completion (`velero restore wait --timeout 15m`)
5. Assert `RestorePhase == Completed` (not PartiallyFailed, not Failed) — exit 1 on any other phase
6. Delete `velero-restore-test` namespace
7. Delete the Restore CR

`--include-cluster-resources=false` prevents the restore from conflicting with live cluster-scoped resources. `--namespace-mappings` redirects the monitoring namespace into the ephemeral test namespace — ArgoCD does not manage `velero-restore-test`, so there is no sync conflict.

**RBAC:** `ServiceAccount` + `ClusterRole` + `ClusterRoleBinding`, all named `velero-restore-drill`.

ClusterRole permissions:
- `velero.io`: `backups` → `get`, `list`; `restores` → `create`, `get`, `list`, `delete`, `watch`
- core: `namespaces` → `create`, `delete`, `get`

Namespace management requires ClusterRole (cluster-scoped resource). All three manifests (`serviceaccount.yaml`, `rbac.yaml`, `cronjob.yaml`) live under `resources/`.

### 6. PrometheusRules — `kubernetes/base/monitoring/backup-alerts/`

ArgoCD Application + `resources/prometheusrule.yaml`. `project: monitoring`. Prometheus picks up PrometheusRules cluster-wide via `ruleSelectorNilUsesHelmValues: false`.

Five rules:

| Alert | Expression | Severity |
|---|---|---|
| `VeleroBackupMissed` | `(time() - velero_backup_last_successful_timestamp{schedule!=""}) > 90000` | warning |
| `VeleroBackupFailed` | `increase(velero_backup_failure_total[2h]) > 0` | critical |
| `VeleroBSLUnavailable` | `velero_backup_storage_location_available == 0` | critical |
| `EtcdSnapshotStale` | `(time() - kube_cronjob_status_last_successful_time{cronjob="etcd-snapshot-health", namespace="kube-system"}) > 36000` | warning |
| `VeleroRestoreDrillMissed` | `(time() - kube_cronjob_status_last_successful_time{cronjob="velero-restore-drill", namespace="velero"}) > 2678400` | warning |

All route to the existing `email` receiver (mydellpc07@gmail.com) via the already-configured Alertmanager.

### 7. Grafana Dashboard — `kubernetes/base/monitoring/backup-dashboard/`

ArgoCD Application + `resources/dashboard-configmap.yaml`. ConfigMap with label `grafana_dashboard: "1"` — the kube-prometheus-stack sidecar provisions it automatically.

Panels: last backup timestamp per schedule, backup count over 7 days, BSL availability status, etcd health CronJob last success, restore drill last success.

### 8. Justfile Recipes

Three new recipes:

- **`velero-status`** — `velero backup get` + `velero restore get`, formatted for quick triage
- **`velero-restore BACKUP NAMESPACE`** — prints argocd auto-sync disable command for the target namespace, creates the restore, waits, prints re-enable instructions. Does not disable sync automatically — operator must confirm before and after.
- **`etcd-restore`** — prints the full manual procedure: download snapshot from R2 via `aws s3 cp` (credentials passed via CLI, not Secret, since apiserver is down), stop k3s on all nodes, `k3s server --cluster-reset --cluster-reset-restore-path=<snapshot>` on one CP node, restart remaining CP nodes in order.

## Data Flow

```
k3s (all CP nodes)
  └─ every 6h ──► etcd snapshot (compressed) ──► R2: arunanshu-etcd-snapshots/prod/
                                                        ▲
etcd-snapshot-health CronJob (every 8h, kube-system) ──┘
  └─ lists bucket, checks recency ──► exit 0/1
       └─ kube_cronjob_status_last_successful_time ──► EtcdSnapshotStale alert

Velero controller (daily 02:00)
  └─ full cluster backup ──► R2: arunanshu-velero-backups/
       └─ metrics :8085 ──► ServiceMonitor ──► Prometheus
            └─ velero_backup_last_successful_timestamp ──► VeleroBackupMissed alert

velero-restore-drill CronJob (monthly, 1st 08:00)
  └─ restores monitoring ──► velero-restore-test namespace
       └─ asserts Completed ──► exit 0/1
            └─ kube_cronjob_status_last_successful_time ──► VeleroRestoreDrillMissed alert

Prometheus ──► PrometheusRules ──► Alertmanager ──► email (mydellpc07@gmail.com)
```

## Restore Paths

**Scenario 1 — Single namespace/resource loss** (~30 min):
`just velero-restore BACKUP_NAME NAMESPACE`. Disable ArgoCD auto-sync on the target namespace first (recipe prints the command). After restore verification, re-enable. ArgoCD will reconcile any diff between restored state and git.

**Scenario 2 — Full cluster rebuild from scratch** (~45 min):
GitOps path: `tofu apply` → bootstrap sequence → `just argocd-root-bootstrap` → ArgoCD converges. Velero optional for recovering dynamic state not in git.

**Scenario 3 — etcd restore** (last resort, manual):
`just etcd-restore` prints the procedure. Note: S3 credentials must be passed directly via CLI (`--etcd-s3-access-key`, `--etcd-s3-secret-key`, `--etcd-s3-endpoint`, etc.) since the apiserver and SealedSecrets controller are unavailable during restore.

## Non-Goals

- PV data backup (FSB) for any current workload
- Tempo S3 backend migration
- Automated etcd restore drill
- Velero UI deployment
- Cross-region R2 replication (R2 is single-region Ceph; bucket versioning + delete protection is the accepted posture for homelab scale)
- Renaming or restructuring the existing monitoring AppProject
